# 项目拆解与完善路线

## 1. 项目一句话

这是一个基于 CrewAI 的多 Agent 自动化投研系统，输入公司名称或 ticker 后，系统会自动完成公司解析、市场情报搜集、监管文件复核、财务分析、投资备忘录生成，以及结构化建议和 watchlist 更新。

## 2. 为什么这个项目值得讲

这个项目的价值不只是“调用大模型生成报告”，而是把一条真实业务链路拆成了多个角色、多个任务、多个工具和多个中间产物。

它体现了 4 类能力：

- Agent 系统设计能力
- 外部 API 集成能力
- Python 工程化能力
- 面向业务场景的产品思维

## 3. 最适合对外介绍的主线

推荐你按下面顺序讲，不容易乱：

1. 先讲业务问题
   - 分析师做投研初稿时，最耗时的不是结论判断，而是前置的资料搜集、财报定位、财务整理和初稿搭建。
2. 再讲系统设计
   - 我把流程拆成 3 个 Agent 和 4 个 Task，让不同角色只做自己擅长的步骤。
3. 再讲工程实现
   - 系统接了搜索、SEC、PDF、财务计算和本地持久化，同时保留中间产物和评估指标。
4. 最后讲项目价值
   - 它把“研究准备工作”自动化，减少重复劳动，让人工把时间放在判断和复核上。

## 4. 项目怎么拆

### 4.1 输入层

- `main.py`
  - 负责 CLI 参数读取、运行目录准备、工作流输入组装、失败兜底和标准产物落盘。
- `resolver.py`
  - 负责把模糊公司名解析成标准公司实体和 ticker。

### 4.2 编排层

- `crew.py`
  - 负责定义 3 个 Agent、4 个 Task 以及顺序执行关系。
- `config/agents.yaml`
  - 负责角色设定。
- `config/tasks.yaml`
  - 负责任务目标和输出约束。

### 4.3 能力层

- `tools/investment_tools.py`
  - 负责搜索、SEC、PDF、HTTP 重试等外部能力。
- `finance.py`
  - 负责确定性财务指标计算。

### 4.4 治理层

- `evaluation.py`
  - 负责记录任务耗时、API 失败率、财务字段覆盖率、artifact 完整性。
- `recommendation.py`
  - 负责从最终报告抽取结构化建议、风险、催化剂和 trust score。
- `watchlist.py`
  - 负责本地观察池的持久化管理。

## 5. 当前最能打的亮点

### 亮点一：不是单 Agent，而是显式分工

- 信息搜集、财报分析、报告撰写分别由不同 Agent 负责。
- 这样更容易控制 prompt、工具权限和问题定位。

### 亮点二：不是黑盒输出，而是保留中间产物

- 每一步都有独立 markdown 输出。
- 出现问题时可以快速判断是搜索差、财务差，还是最终汇总差。

### 亮点三：不是只拼 LLM，而是接了真实数据源

- Google 搜索
- SEC filing
- SEC company facts
- 本地 PDF 文本提取
- 财务指标计算

### 亮点四：不是只看“能不能生成”，而是开始做评估

- 有运行耗时
- 有 API 成功率
- 有 artifact 完整性
- 有 trust score

## 6. 当前最真实的短板

### 短板一：数据源偏 SEC / 美股

- 当前代码能力和目标市场之间还存在不完全匹配。
- artifacts 里已经跑了港股和 A 股样例，但工具层仍然更偏 SEC 体系。

### 短板二：结构化结果还偏规则抽取

- 当前 recommendation 主要从 markdown 中提取 summary、catalysts、risks。
- 它适合轻量产品化，但还不是最稳的结构化生产方式。

### 短板三：持久化还是本地文件

- `watchlist.json` 很适合原型阶段。
- 但如果要支持多用户、批量查询、历史对比，就需要数据库。

## 7. 这次轻量完善做了什么

### 已补强项

- 增强了 `recommendation.py` 的章节识别能力。
- 现在可以识别带 emoji 或修饰语的二级标题，而不只支持完全标准标题。
- 现在支持从 markdown 表格中提取风险和催化剂，不再只依赖 bullet list。
- 新增回归测试，覆盖“装饰标题 + 表格输出”的真实报告场景。
- 新增 `--watchlist-rebuild` CLI 入口，可以基于已有 artifacts 重建结构化建议和 watchlist。

### 这项改动的价值

- `06_structured_recommendation.json` 更容易产出完整字段。
- `watchlist.json` 的展示质量会更稳定。
- 项目讲解时可以更自然地说：我不仅生成报告，也做了结构化消费层。
- 即使不重新跑整条工作流，也能修复历史产物中的空字段，便于演示和复盘。

## 8. 下一步最值得继续做的 3 件事

### 方向一：多市场数据源

- 补港股和 A 股的监管/财务数据源。
- 让“目标市场”和“真实工具能力”更一致。

### 方向二：结构化输出升级

- 让关键 Task 直接输出 JSON / Pydantic，而不是完全依赖 markdown 反抽。
- 这样下游 API、前端和数据库会更好接。

### 方向三：Flow 化和人工审核

- 在最终投资建议前增加人工审核节点。
- 让项目从顺序原型升级为更接近企业工作流的系统。

## 9. 如果你的目标是找实习，最推荐的继续完善顺序

1. 先把这个项目讲清楚
   - 一句话版本
   - 2 分钟版本
   - 技术深挖版本
2. 再补最能量化价值的指标
   - 成功率
   - 单次生成耗时
   - 人工修改率
3. 最后再做产品化增强
   - 前端展示
   - 数据库
   - 定时任务

## 10. 面试时容易被问到的问题

### 为什么不用一个 Agent 全做

- 因为投研流程天然分工明确。
- 拆开之后更容易控制工具权限、上下文和失败定位。

### 为什么中间产物要落文件

- 因为这类工作流的关键不是“最后答案”，而是“过程是否可复盘”。

### 为什么还要单独做 `finance.py`

- 因为财务指标属于确定性逻辑，不应该完全交给模型心算。

### 这个项目最难的地方是什么

- 不是把模型接起来，而是让流程稳定、可控、可观察、可验证。

## 11. 一句话结论

如果你把这个项目继续沿着“多市场数据 + 更稳结构化输出 + 更强评估”三条线迭代，它就会从一个不错的 Agent 项目，升级成一个很能打的求职作品集项目。

## 12. 现在能不能算成功

可以把当前版本定义为一个**成功的 MVP 项目**，理由是：

- 已经能完成端到端主链路，而不是停留在局部 demo。
- 已经有 markdown 交付物，也有 JSON 结构化输出。
- 已经能基于历史 artifacts 重建 watchlist 和结构化结果。
- 已经有评估指标、失败兜底和自动化测试。

如果按“投产级系统”标准，它当然还没完成；但如果按“实习求职作品集里一个完成度高、能讲清楚、能跑通、能验证的项目”标准，它现在已经是成立的。
